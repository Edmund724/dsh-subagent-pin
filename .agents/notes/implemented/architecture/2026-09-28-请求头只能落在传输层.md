# 请求头只能落在传输层

2026-09-28。给 OpenCode Go 的请求带上**每个会话自己的** `x-opencode-session`。
本文只留决策本身、逐项核实过的位置、以及排除掉的选项；怎么用、为什么这么用见
`README.md`「OpenCode Go 的会话头」，接缝的实现理由见 `opencode-session.js` 文件头。

## 结论

落点只有一个：补 `globalThis.fetch`，用 `llm/stream` 的作用域把改写限定在一次模型
调用之内。第二次重启前的现场证据（`mode: inject` 一轮）显示：作用域内的 5 条
`POST opencode.ai/zen/go/v1/messages` 全部改写成功，顶层会话
`session-bce8912d…`、它的 `session-title` 辅助调用、子代理的裸 UUID
`f6af83ce…`、本会话 `session-a4a14f50…` 都拿到自己的 id，网关全部 200。

随后正式行上线、路由里的静态头按决定删除，同一台机器再复跑一轮：父会话、新会话与
子代理的回复全部正常。网关强制要这个头（不带会 `400 MissingSessionID`），所以这一轮
同时证明了「值只能来自本行」与「本行写的每会话 id 被接受」。

## 核实的接缝（每一项都在 DSH master `21638c563` 上读过源码）

- `llm/stream` 的 payload 是 `GenerateOptions`：**没有 `headers` 字段**，而且循环构造
  的那一份被深冻结，监听器改它就是抛错。签名只有
  `(options: GenerateOptions, next: () => AsyncIterable<StreamChunk>)`，没有第三个参数。
- `GenerateOptions.sessionId`（`SessionHeader.id`）就是会话 id，顶层是
  `session-<uuid>`，子代理与 ACP 子是裸 UUID；它随会话保存，跨轮次、resume、
  compaction、重试都稳定 —— 正是网关要的「一个会话一个 id」。
- `llm-pi-ai` 的请求头只来自**静态**路由配置（`requestHeaders(profile.headers)`），
  没有任何 per-request 通道。
- `ctx.deepseekLlmApiExtensions` 只服务 `deepseek-official` 那一家，轮不到这里。
- `registerAdapter` 接管 `opencodego` 会以 `DUPLICATE_ADAPTER` 失败。
- 上游 pi-ai ≥ 0.86.0 的 `withOpenCodeSessionHeader` 包的是 **catalog 工厂**
  （`reuseCatalogProvider`）；本环境那条路由手写了 `api: anthropic-messages`，走
  `PROTOCOLS` 现场构造 provider，**永远不经过那个 wrapper**。而 DSH 仍钉
  `@earendil-works/pi-ai ^0.85.1`（`^0.85.1` = `>=0.85.1 <0.86.0`，0.86/0.87 都排除）。

## 排除的选项

- **等 DSH 升 pi-ai**：等不到（无 release），而且就算升了也够不到手写 `api:` 的路由，
  这一条自己就足以否掉。
- **补 `resources/app.asar` 里的 pi-ai**：每次桌面版本更新都会被覆盖；而且改的是
  catalog 工厂那一层，同样够不到 `api:` 覆盖的路由。两处独立失效，任何一处都足以否掉。
- **`localStorage` / profile patch 里的静态头**：这正是被替换掉的现状 —— 全机器共用一个
  值，网关按会话计费与限流的语义无从谈起。
- **`ctx.effect` 之外的长期挂载**：不需要，也不该。插件卸载必须能还原传输层，
  这由 refcount + `ctx.effect` 保证（`test/opencode-session.test.mjs` 有对应断言）。

## 值：派生，而不是原值

上面的现场证据用的是原始会话 id —— 那是第一轮的实现。定稿改成**由会话 id 派生**：
`SHA-256(sessionId)` 的前 16 字节，按 v4 UUID 形状输出（版本位、变体位照 v4 置好）。
理由是原始 id 会把本地会话日志的把手交给第三方，而网关要的只是「同一会话恒定、
不同会话不碰撞」；形状沿用 UUID，因为那是网关实测接受过的形状（`session-<uuid>`
与裸 UUID）。

为什么不是「随机 id + 映射表」：映射表是本行唯一需要存的东西，而它的失败模式全都
落在需求本身上 —— 冷恢复要在第一次请求前读到映射，存储被清 / 换机器 / 重建 profile
就会让同一个会话拿到新值，正好破掉「每会话恒定」；还要额外处理清理、并发写与
「读不到映射时怎么办」（回退原值或随机都语义不一致，报错违反 fail-open）。派生是
纯函数，这些成本一项都不存在，冷恢复也不需要读回任何东西。

未加盐是刻意的：会话 id 本身就是高熵 UUID，加盐只会让"按网关日志里的值反查本地
会话"这件事做不成。因此它防的是日志与网关侧直读原 id，不是不可反推。

一个副作用值得记下：派生让「id 含非法字符」这一失败模式消失了 —— 进 `Headers` 的
永远是摘要，注入不了第二个头，所以那条测试从「坏 id 就不带头」改成了「坏 id 也照样
带安全值」，另外用「URL 判不出来」来覆盖 fail-open。


## 代价与它换来的东西

传输层是全局的，所以代价写在明面上：一次 `globalThis.fetch` 替换，靠
`AsyncLocalStorage` 把作用域收回到「一次 `llm/stream`」；不在作用域内的请求、非 POST、
provider 前缀与网关域名都不匹配的请求，原样透传。作用域必须跨住整个异步迭代 ——
流式适配器是在消费者 pull 的时候才碰传输层，所以 `inScope()` 是逐次 pull 重新进入
作用域，而不是 `als.run` 包一层就完（这一条最初的测试写成 `als.run` 传播，
在合成生成器交接处不成立，测试改成直接调用接缝的方式反而是对的）。

判断失败一律 fail-open：判不出来就透传原参数，绝不让一个坏 session id 把健康的模型
调用变成硬失败；但传输层自己的异常照常抛出，不被吞掉。
