# 强度不是插件的承诺

## 这份笔记是什么

2026-09-27 架构评审的**候选 6**：「`reasoningEffort` 是不透明字符串，而路由决策可以把它作废」。笔记记下这件事的结论 —— 为什么插件不校验强度、配置面收到什么程度、以及一处刻意不跟随的差异。`CONTEXT.md` 的「已排除」只留一行摘要，完整理由住在这里。

## 决定（2026-09-27）

1. **配置面收成 Host 的词汇。** `config.reasoningEffort` 是 DSH 自己的七个 thinking level（`config-schema.js` 的 `THINKING_LEVELS`：`off`/`minimal`/`low`/`medium`/`high`/`xhigh`/`max`）。写别的值是激活错误，报错自带字段路径。
2. **插件不按路由校验强度。** 不调 `llm.resolveModelInfo` / `llm.resolveCallConfig`，不 clamp、不丢弃、不改写，也不因此改路由；不新增 `llm` 依赖，不把 `apply` 或 `plan()` 改成 async。
3. **强度是否被落到的模型接受，由 DSH 在请求路径回答。** 插件只声明「想用哪个强度」。

## 为什么：DSH 自己的三层（本轮逐条核实）

- **配置面只认词汇，不认模型。** provider profile 的 `reasoning` 字段是 `z.union(THINKING_LEVELS)`（`llm-pi-ai.js:296–305` 定义、`:1025` 声明），七个 level，永远不按模型校验。
- **描述面取不到就当没有，绝不报错。** `describableReasoningLevel`（`llm-pi-ai.js:1696–1698`，用在 `:1815` 造模型目录）把「这个模型不支持的配置 level」变成 `undefined`。它的 JSDoc 写明理由：目录一旦失败，整条 provider 会从所有选择器里消失，一个配错的字段不该藏起整条路由的模型 —— *"The request path still refuses, which is where a bad configuration belongs."*
- **请求面拒绝，消息点名。** `resolveReasoningLevel`（`llm-pi-ai.js:1700–1705`，用在 `:1847` 的 `options.reasoningEffort ?? profile.reasoning`）抛 `UNSUPPORTED_REASONING_EFFORT`：`pi-ai provider "P" model "M" does not support reasoning effort "X"`，注释写明 *without invoking pi-ai's clamp*。`dsh-llm` 的 `resolveCallConfig` 是同一道闸（`dsh-llm.js:2151–2163`：*Unsupported explicit efforts reject before provider I/O; no clamping or aliasing is performed*）。**没有任何提前反馈**：选择器里看不到错，错配只在第一次真正解析请求时抛。

插件若自己校验，就是给同一件事加第二个判定点和第二套消息 —— 这正是这份代码一直在避免的第二个权威。配置面收紧与这三层同构：只检查「是不是一个已知 level」，不检查模型。

## 已考虑并否决

- **每次委派用 `resolveCallConfig` 校验。** 代价：`llm` 成为新的 Host 依赖（缺失语义还要再定）、`plan()` 变 async（接缝的包装器跟着变）、每路由要自建缓存（Host 两端都无 memo）。
- **`settings` 模式禁止 `reasoningEffort`。** DSH 从不为「模型不匹配」拒绝一份配置，这条与它的分层相反。
- **`pinned` 模式激活期校验。** 为一条潜伏问题把 `apply()` 改成 async：Cordis 只在插件函数**没有** `prototype` 时才 await 它的返回值（`cordis-fiber.ts:250–261` 的 `isConstructor` 分支），普通 `function apply` 是被 `new` 调用的、返回值被丢弃；`await` 期间被卸载还会让随后的 `ctx.effect` 抛 `INACTIVE_EFFECT`。asar 内也没有任何已发布插件在激活期调 llm 校验。
- **静默丢弃配置强度。** 与仓库「不静默」的哲学相反，也让这个键失去意义。
- **删掉 `reasoningEffort`。** `pinned` 模式（没有 Settings 行的 Host）会失去唯一表达强度的能力。

## 一处刻意不跟随的差异

插件注入的 effort 在 Host 眼里是**显式**（`requested.reasoningEffort !== void 0`），所以 Host 那两条「路由变了就丢掉 inherit/配置 effort」的清理不会作用于它：`subagent-index.js:450`；工具侧的同类规则见 `tool-subagent-index.js:71–74`。后果是：随包配置（不设 effort）换模型时子代理静默用新模型的默认强度，而一旦配置了 effort，换模型后变成请求期报错。

要跟随那条清理，插件得先知道父/基线路由（接缝里拿不到），代价与引入 `llm` 依赖同级，收益只是把「报错」换成「静默用模型默认」。所以不跟随，写在这里。

## 代价与纪律

`THINKING_LEVELS` 是 pi-ai 的内部常量，不是可导入的接口，插件只能硬编码同一组词。因此 README「已验证」的升级核对清单里多了一条**不靠包版本**的耦合：Host 新增 level 时要在 `config-schema.js` 里补上，否则 schema 会拒掉一个 Host 已经认识的强度。单元的 `test/config-schema.test.mjs` 钉住这七个 level 的接受与拒绝。
