# 升级了也不跟着走

2026-09-29。DSH `0.2.0-rc.2` 把 pi-ai 从 `^0.85.1` 升到 `^0.87.1`，pi-ai 从 0.86.0 起自带的
`withOpenCodeSessionHeader` 因此随包进了这台机器。本文记三件事：为什么升级仍不构成替代、
为什么 `opencode-header` 的形态照旧、以及每条结论在哪里核实过。

## 结论

本行承诺两件事，缺一不可：**网关要的那个头名**，和**由会话 id 派生、原始 id 不出机器**的值。
pi-ai 在场的那条路最多满足第一件，而且连第一件都只对一种路由形态成立：

1. **够不到。** `withOpenCodeSessionHeader` 不在调用参数上，而在 **provider 的 api map** 里 ——
   它只包在 `opencodeGoProvider()` / `opencodeProvider()` 这两个 catalog 工厂造出的 provider 上。
   宿主只有 `catalog !== undefined && spec.api === undefined` 时才复用 catalog provider；
   `opencodego` 手写了 `api: anthropic-messages`，走协议表 `createProvider`，永远不复用。
2. **值是原值。** 即使够得到，它发的也是 `options.sessionId` 本身，派生值不在其内。
3. **还有一条关不掉的路。** Responses 那条不看任何 `compat` 布尔量：只要 `sessionId` 在、
   cache retention 不是 `none`，就把原值写进 `session_id` 与 `x-client-request-id`。

所以形态照旧：本行自己在传输层写派生值。不跟随 pi-ai 的会话头，也不把「值」寄望于上游的
可配置项 —— 一个不承诺这两件事的实现，不能承担本行的承诺。

## 核实的接缝

- **wrapper 的形状**：`dist/providers/opencode-headers.js` 全文 —— `withSessionHeader` 在
  `sessionId` 缺失或同名头（大小写无关）已存在时原样返回，否则写 `x-opencode-session` =
  `options.sessionId`。
- **wrapper 的落点**：`dist/providers/opencode-go.js` 与 `dist/providers/opencode.js` 的工厂里，
  它包的是 `anthropicMessagesApi()` / `openAICompletionsApi()` / `openAIResponsesApi()` 的返回值，
  也就是 provider 的 `api` map。
- **宿主的岔路**：`packages/llm/llm-pi-ai/src/provider.ts` —— 先问 `catalogProvider(spec.provider)`，
  只有 `catalog !== undefined && spec.api === undefined` 才 `reuseCatalogProvider`；其余从
  `PROTOCOLS` 取协议实现现场 `createProvider`，而那张表导入的是**未包过**的 API 实现。
- **三条兼容路**：`dist/api/anthropic-messages.js`（`sendSessionAffinityHeaders ?? false`）、
  `dist/api/openai-completions.js`（默认 `isOpenRouter`）、`dist/api/openai-responses.js`
  （`if (sessionId)`，无开关）；`dist/providers/data/opencode-go.json` 里没有一个模型打开开关。
- **配置面也打不开**：rc.2 的 `packages/llm/llm-pi-ai/src/catalog.ts` 把
  `sendSessionAffinityHeaders` 与 `sessionAffinityFormat` 在三个 compat 闸门里都标成 `withhold`，
  写它就是配置错误（"pi-ai's installed catalog sets it for the vendors that need it, so name that
  provider as the route instead"）。
- **宿主没有新缝**：`GenerateOptions`（`packages/llm/llm/src/types.ts`，两个 tag 逐 blob 相同）
  仍然只有 `sessionId`，没有 `headers`；`llm/stream` 的 payload 深冻结；adapter 交给 pi-ai 的
  `headers` 仍然只来自静态 `profile.headers` 加归属信息。pi-ai 侧也没有新增 caller-facing 通道 ——
  `ProviderRequestOptions.headers`、`StreamOptions.sessionId`、`ModelsRequestTransforms.transformHeaders`
  在 0.85.1 就都在。

## 排除的选项

- **改成 catalog 路由、删掉本行**：唯一能换来「pi-ai 自己发头名」的做法，代价是三样 —— 值变原值；
  模型清单回到 catalog（本环境的两个模型是手写的）；Responses 那条关不掉，原值照发。
- **在路由上打开 `compat.sendSessionAffinityHeaders`**：头名不是网关要的那个，而且宿主把这几个
  compat 字段列为 withheld，配置面直接拒。
- **等宿主开 per-request headers 缝**：rc.2 的 `packages/llm/llm` 只有 release 提交，
  `GenerateOptions` 一个字段都没动；承诺不能排在一件没人答应的事后面。
- **打 pi-ai 的模块**：桌面每次升级都会覆盖，而且 ESM 命名空间不可写。
- **让本行也发原值，以少写几行**：两个承诺只剩一个，手写路由还照样发不出去。

## 代价与边角

- 传输层是全局的，代价（作用域、fail-open、引用计数）见
  [请求头只能落在传输层](2026-09-28-请求头只能落在传输层.md)。
- 一条今天不适用、换路由形态时要看的边角：Responses 那条路除了两个头，**请求体的
  `prompt_cache_key` 也从同一个 `sessionId` 算**（`clampOpenAIPromptCacheKey`）。那不是头，
  本行管不到 —— 手写 `anthropic-messages` 路由不会走到它。
- 同名头替换现在是承重语义：pi-ai 一旦先盖了原值，本行的 `Headers.set` 必须压住它。两条测试钉住
  这件事（含 pi-ai 那种大小写与 `Headers` 实例的写法），见 `test/opencode-header.test.mjs`。

## 复核

改动或升级后要看的三处：`docs/opencode-header.md` 的三条路表（头名、值、今天成立吗）、
`npm test`（`opencode-header` 那组，尤其是同名头两条），以及 `docs/verification.md` 的现场核对表
「OpenCode Go 会话头」两行 —— 后者验的是那一次运行，不能替代前两者。
