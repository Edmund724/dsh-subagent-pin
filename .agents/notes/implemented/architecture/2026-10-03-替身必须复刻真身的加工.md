# 替身必须复刻真身的加工

2026-10-03。转向那行两次「整行看起来正常、实际没生效」的根因，以及由此定下的替身纪律。
合并这件事本身见 `2026-10-03-子代理转向行并进本包.md`；Host 形状假设在
`subagent-steer.js` 文件头，判据的守卫在 `test/subagent-steer.test.mjs`。

## 结论

`test-support/steer-doubles.mjs` 的 `tools.register()` 必须与真身一样校验
`output { schema, render }` 与 raw JSON Schema 子集；seed 出来的 `send_message`
定义必须是 `defineTool` 编译**之后**的形状（`parameters.properties`），并且有一条
测试断言它落在 raw 子集内。移植的边界写在 `test-support/json-schema-subset.mjs` 的
文件头。

## 两次踩坑

### 一、写入侧：定义写成了作者方言

定义按 `defineTool()` 的**作者方言**写（属性级 `required: true`），却直接交给
`ctx.tools.register()`。`register()` 把 `output.schema` 当 **raw JSON Schema** 校验，
`assertSupportedJsonSchema` 抛 `UNSUPPORTED_SCHEMA`（`schema.properties.messageId.required
is not supported on type "string"`），`apply` 抛出 → fiber 进入 FAILED → 两个工具、
guard 与提示段全部回滚。

所有 inspect 面看起来都正常：`Tool.listTools` 里没有工具（当时被读成"还没加载"），
`Config.listConfigs` 给的是 `status: absent` —— 而那只表示「本行没有 Config schema」，
与有没有加载无关；只有 `plugin_manager list_plugins` 的 `fiberPhase: failed` 说出真相。
替身当时只收不校验，正是这个盲区让「真身必抛的定义」一路绿灯。

### 二、读取侧：判据读的是作者方言的形状

`isNameAddressed()` 当时判的是 `'target' in parameters`，而 `defineTool()` 在**定义时**
就把作者方言编译成 raw JSON Schema（`parameterSchemaSpecToJsonSchema`，
`dsh-tools/lib/index.js:802`，在 `:848` 调用）：`target` 永远在 `parameters.properties`
之下，顶层没有 `target`。判据因此恒为假，guard 对每一次真实调用都**静默弃权**，
而它本该拦的那句话原样漏了过去。

测试全绿的原因与第一条同源：`seedSendMessage()` 注册的是作者方言的平铺形状
`{ target: {}, message: {} }`，跳过了真身的编译步骤，所以替身永远不会以真身的方式失败。

## 纪律

替身只收不校验，或者按作者方言摆 seed，都会让「真身必抛」或「真身必假」的定义绿灯。
这条线的两侧都要复刻：**写入侧**复刻 `register()` 的两项校验（`output { schema, render }`
与 raw 子集），**读取侧**只按注册表持有的形状（`parameters.properties`）判断，seed 的
定义也必须落在 raw 子集内 —— 三者各有一条测试点名。
