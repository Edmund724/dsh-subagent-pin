# 接缝与已排除

## 这份笔记是什么

本插件是装在包外的一行 Host 插件，它真正依赖的 Host 形状只有一处：**`ctx.subagents` 实例上的 `start` / `startContinuable` 两个方法**。这份笔记记下三件在别处不再重复的事：

- **(a) 接缝地图的结论** —— 为什么接缝只能落在这两个实例方法上，不能落在别处；
- **(b) 两条已排除的方案** —— `CONTEXT.md` 的「已排除」一节只留标题与一句摘要，完整推理住在这里；
- **(c) 2026-09-27 的文档分区决定** —— 为什么词表留在 `CONTEXT.md`、决策记录住在这里。

读者不是插件使用者。本仓文档分两层：`README.md`（中文，无后缀 = 主）与 `README-en.md`（完整互译）是人类手册，只引用、不复述；`CONTEXT.md` 是词与判据，各模块 JSDoc（`route-policy.js:1–34`、`config-schema.js:1–28`、`host-contract.js`）是实现者层。这份笔记是第四层，只服务未来的维护者与评审；它随仓库走，**也随包发布** —— `README.md` 的散文点名了 `.agents/notes` 这个路径，`test/docs.test.mjs` 的守卫要求被点名的仓库路径落在 `package.json` 的 `files` 里，因此打包产物上 `npm install && npm test` 跑得出与仓库一致的 108 项。

**为什么归 `implemented/` 而不是 `archived/`。** `implemented` 收的是当前仍然生效的决策，文件名即决策日期；`archived/` 收的是被后续决定取代的历史。本文的 (a) 与 (b) 描述的都是**现在这份代码**：接缝仍然在 `start` / `startContinuable` 上，`ctx.effect` 仍然不进契约。只要 Host 契约没变，它们就一直有效，没有被任何后续决定取代，所以属于 `implemented`。若哪天接缝整体迁移、或这两条排除被重新采纳，改的是本文件并把新的一份放进 `implemented/`，本文件再迁 `archived/`。

## (a) 接缝地图的结论：为什么只能包实例方法

以下六条引自 2026-09-27 的架构评审报告，括注里的位置是本轮对照解包后的 DSH lib（`D:\DSH\asar-tool\`，35 个文件；`D:\Apps\DeepSeek Harness\resources\app.asar` 是单个归档文件、不是目录）重新核实到的 `文件:行号`。

1. **`Context.intercept` 只供服务配置，`subagents` 的 Config 里也没有路由字段。**
   `intercept()` 的全部契约就是「把 config 合并进该服务的 resolved config」，没有别的语义——见它的 JSDoc 与实现（`cordis-context.ts:127–145`，实现在 `:141–145`；fiber 侧按服务名落进 `Context[symbols.intercept]`，`cordis-fiber.ts:240–243`）。随包发布的 `base.cordis.patch.yml` 里没有任何一行用 `intercept`（全文件 0 命中）。而 `subagents` 的整张 Config 只有两个字段：`maxDepth` 与 `maxActiveSubagents`（`subagent-index.js:2821–2824`）。没有路由字段，就没有「配一个值来改变委派路由」的官方入口。

2. **`provider.start()` 全仓只有 dsh-subagent 一处调用，无第三方旁路。**
   整个解包后的 lib 里 `provider.start(` 只出现一次，就在 `subagents.start()` 内部（`subagent-index.js:3129`）。一次委派要落到某个 provider，必须先过 `subagents` 这一层。

3. **delegation 工具、workflow `agent()`、`agentTeams.spawnTeammate`、嵌套委派，四条路径都汇进同一个 `ctx.subagents`。**
   - delegation 工具（模型面）：`ctx.subagents.startContinuable(...)`（`tool-subagent-index.js:527`）与两处 `ctx.subagents.start(...)`（`:548` 后台 one-shot、`:557` 前台），都取自同一个 `runtimeCtx`。
   - workflow 的 `agent()`：对外说明在 `tool-workflow.js:143`；实现在 `workflow-ptc.js`——该插件 `inject` 了 `subagents`（`:581`），运行期绑定 `const subagents = runCtx.subagents` 并交给 `PtcWorkflowRun`（`:631–632`），脚本里的 `agent()` 落到 `this.subagents.start(this.provider, {...})`（`:328`）。
   - `agentTeams.spawnTeammate`：定义在 `agent-team-runtime.js:1764`，真正起子代理走 `this.ctx.subagents.startContinuable({...})`（`:573`）；工具侧入口 `tool-agent-team-index.js:271`。
   - 嵌套委派：delegation 工具注册在共享的 `tools` 服务上（`tool-subagent-index.js:398`），所以子代理手里仍然有这个工具；递归预算正是 `maxDepth` / `depthLimit` 这一对（`tool-subagent-index.js:269`、`:377`、`:508`；`subagent-index.js:400–405` 的 `resolveChildDepth`）。子代理再委派时走的仍是上面同一个 `ctx.subagents`。

4. **`assertCapabilities` 只在 `start` 上被调用（continuable 路径不查该标志）→ 豁免策略在两个方法上语义不同。**
   定义在 `subagent-index.js:3173–3197`，全文件唯一的调用点是 `start()` 内的 `subagent-index.js:3117`；`provider.capabilities[...]` 也只有 `subagent-index.js:3196` 一处读取。continuable 那一侧，`startContinuable`（`:2879–2881`）转给 `requireContinuations().startContinuable(spec)`，再由 `prepareContinuable`（`:3149–3152`）检查**方法是否存在**（`provider.prepareContinuable === void 0`），并不读 `capabilities` 记录。于是：读不到 `capabilities.agentOptions` 时，`start` 应当把委派原样交给 provider 自己路由；同一个判断在 `startContinuable` 上根本没有这种读法，插件必须先确认 `inheritsParentContext`，才谈得上 `inherited` 豁免。

5. **Cordis 的 `getTraceable → createTraceable` 每次读函数属性都新建包装 → 函数值身份不可能稳定，只有 property descriptor 稳定。**
   `getTraceable`（`cordis-utils.ts:117–125`）转调 `createTraceable`（`:165–218`）；它的 `get` 陷阱（`:174–200`）**每次读属性都新建一个包装**：命中 tracker 就 `createTraceable(...)`（`:193`），否则对函数走 `createShadowMethod(...)`（`:196`），而后者本身就是 `new Proxy(value, ...)`（`:156–163`）。所以 `ctx.subagents.start === ctx.subagents.start` 恒为 false，任何以捕获的函数身份为基准的包装法都不成立。**属性描述符则稳定**：该 proxy 的 handler 只定义 `get`（`:174`）、`set`（`:201`）、`apply`（`:213`）三个陷阱，没有 `defineProperty` / `deleteProperty` / `getOwnPropertyDescriptor`，于是 `Object.defineProperty` / `delete` / 读 descriptor 直接落到服务实例上。插件的包装器因此是一个 *own shadow*，激活与卸载都基于 descriptor 操作——`plugin.js:243`（安装）、`:251` 与 `:266–271`（卸载还原）走的正是这三件事。

6. **冷恢复（`deliverFollowup → coldResume`）不经被包住的两个方法，直接从持久化 descriptor 重建 provider / model / effort。**
   `deliverFollowup` 在 `subagent-index.js:1820–1845`，child 不驻留内存时于 `:1824` 转 `coldResume`；`coldResume`（`:1894–1947`）从持久化事件 fold 出 descriptor（`:1916` 的 `foldSubagentDescriptor`），用 `descriptor.agentProvider` / `agentModel` / `agentReasoningEffort` 重建 `agentOptions`（`:1924–1928`）后 `materialize`（`:1920–1934`）。整个函数不读任何设置，也不调 `start` / `startContinuable`。「清单只在新建委派时求值一次、路由随该 child 冻结在 descriptor 里」是这条的直接后果。

**结论。** 路由这件事，Host 留给插件的唯一入口就是 `subagents` 实例上的 `start` / `startContinuable` 两个方法；而包住它们只能用 own shadow 的 descriptor 手段，不能用捕获的函数身份。

### 本轮未能重新核实的条目

- **「`provider.start()` 全仓只有一处调用」** 中的「全仓」：本轮只扫了 `D:\DSH\asar-tool\` 这 35 个解包产物。已安装 profile 的 `node_modules` 树与 `app.asar` 归档本身未逐字节搜索。在解包产物范围内成立。
- **「嵌套委派」作为一条独立代码路径**：lib 中没有标为 nested 的委派入口。本条 (a)-3 的第四个子弹是**据共享 `tools` 服务上的工具注册 + `maxDepth`/`depthLimit` 递归预算重建**出来的，不是定位到一条具名路径。其余三条路径均为直接定位。
- **`Context.intercept` 「只供服务配置」**：已从 `cordis-context.ts:127–145` 的 JSDoc 与实现、以及 `base.cordis.patch.yml` 0 命中确认；但未穷举 DSH 全部插件对该 API 的使用方式。

## (b) 两条已排除的完整正文

`CONTEXT.md` 的「已排除」一节只保留这两条的标题与一句摘要，完整推理如下。

1. **不用 `@deepseek-ai/dsh-invariants` 表达这份契约。**
   Harness 升级必然重启，而激活断言每次启动都跑一遍，invariant 提供的「运行时复查」是重复通道；它又受 config 过滤、`fail()` 只杀自己的子 fiber，接不了「拒绝激活」这一层 —— 两个通道就是第二个权威。

2. **`ctx.effect` 的返回值形态与卸载顺序不写进契约。**
   真实语义是「立即同步执行回调 + 把返回的函数登记为 disposer」；差异只在返回值形态（Host 返回可 await 的 disposer 包装，替身返回内层 cleanup）与卸载顺序（无参数、跨 effect 逆序并发），而 `plugin.js` 不使用返回值，差异不承重。必须成立的那半边由 `test/host-contract.test.mjs` 断言。
